### 1.2 沉浸歌词界面闪退专项（最高优先级）

**用户现象**：播放中 15s 无操作自动进入沉浸歌词页后崩溃一次，报错 `Rendered more hooks than during the previous render`（栈中 `at updateRef` → `ImmersiveLayer`）。

**根因（git 证据链）**：
- 相关提交：`6f4f074`（v0.6.2.4 初始版）→ `4d4d29b`（v0.6.2.7）→ `21e7c85`（v0.6.2.8）。
- `6f4f074`/`4d4d29b` 两版 immersiveLayer.tsx 中全部 hooks 均在 `if (!visible) return null` 之前，且当时不存在歌词切换动画 hooks。
- `21e7c85`（提交信息含"沉浸修复"）新增 `slideAnim`/`prevLrcIndexRef` 两个 `useRef` + 一个 `useEffect`（歌词切换平滑动画），已直接放在 `return null` 之前，并附注释：「hooks 必须在组件顶层调用（return null 之前），否则 visible 切换时 hook 数量变化会导致 React 渲染崩溃」。
- 结论：开发者最初把动画 hooks 写在 `if (!visible) return null;` 之后，`visible=false` 渲染 hook 数 22、`visible=true` 渲染 hook 数 24，React 在 `updateRef` 处抛错；修复方式即同一提交内上移 hooks，崩溃版本从未进入 git 历史（仅开发期工作区）。

**当前状态判定：崩溃根因已修复。** 逐行核查当前磁盘代码：immersiveLayer.tsx 全部 24 个 hook 调用均位于 `if (!visible) return null;` 之前、无条件包裹；JSX 条件分支渲染的子元素均为 RN 原生组件；消费的自定义 hooks 内部全部无条件顶层调用；挂载点 `musicDetail/index.tsx` 无 JSX 条件包裹。

### 1.4 P0 问题与修复

**【P0-01】平板覆盖层栈中下层页 `useParams` 被栈顶页参数污染，触发渲染期 TypeError（已修复）**

- 原问题：`useParams` 在覆盖层栈非空时，对所有挂载组件统一返回栈顶页（`subPages[length-1]`）的 params；而 `SubPageOverlay` 把栈内每一页都常驻挂载渲染。栈=[A,B] 时下层 A 每次重渲染拿到 B 的 params。
- 崩溃链路易达：平板搜索 tab → 点歌手（ARTIST_DETAIL 入栈）→ 三点菜单 → 批量编辑（MUSIC_LIST_EDITOR 再入栈）。下层 artistDetail 重渲染取到 `{musicList, musicSheet}`，`artistItem` 变 `undefined`；`artistDetail/components/header.tsx:42` 直接 `artistItem.avatar?.startsWith("//")` → TypeError，渲染期崩溃。
- 同源副作用：`setting(basic)` 内点"关于"入栈后，下层 setting frame 重渲染拿到 `type="about"` → 静默从 basic 切到 about 视图；`albumDetail` 解构 `albumItem` 在栈顶 params=undefined 时同样崩。
- 修复方式：
  1. `router/index.ts`：新增 `TabletFrameParamsContext`（Symbol 哨兵默认值）并导出 `TabletFrameParamsProvider`；`useParams` 重写为——覆盖层帧内优先消费本帧 Provider 注入的 params，否则回退 `route?.params`；**删除原"subPages 栈顶 params"分支**。
  2. `subPageOverlay.tsx`：渲染每帧时用 `<TabletFrameParamsProvider value={page.params}>` 包裹 `<Component />`。
- 验证：tsc 0 错误；全局 `useParams(` 16 处调用点逐一核对。合并时复核：`src/core/router/index.ts:20,25,143` 与 `src/pages/home/components/subPageOverlay.tsx:11,66,68` 确有 `TabletFrameParams` 注入，修复在位。

## 第5章 音源可用率分维度统计改造（2026-10-23）

### 5.1 背景与目标

原可用率统计为"合并单桶"（`recordResult(platform, ok)` 把所有搜索/解析/换源结果累加进同一 success/fail），存在三个问题：
1. **搜索淹没播放**：搜索次数远多于播放次数，一个"搜索结果好但播放全废"的源可用率照样虚高；
2. **解析成功 ≠ 能播**：`getMediaSource` 返回 URL 即记成功，URL 失效/假链接不计真实出声；
3. **无权重**：播放这一最重要维度没有参与计算。

目标：分维度独立统计（search/parse/play/lyric），合成可用率由"播放"主导；歌词、歌单维度独立用于各自的选择排序。

### 5.2 统计内核（src/core/pluginReliability.ts）

- 结构改为分维度记录：`IReliabilityRecord { search?, parse?, play?, lyric? }`，每维各带 success/fail；
- `recordResult(platform, ok, dimension)` 新增维度参数（默认 "search"）；新增语义化包装 `recordPlayResult` / `recordLyricResult`；
- **合成可用率** = 播放 60% + 解析 30% + 搜索 10%，按"有数据的维度"权重归一化（如只有播放数据 → 100% 播放成功率；无任何数据 → 默认 0.5）；
- 歌词维度独立读取：`getLyricReliabilitySync(platform)` / `hasLyricRecordSync(platform)`（供歌词源选择排序）；
- 推荐歌单沿用独立统计（recommendMap，key=PluginRecommendReliability），不受本次维度拆分影响；
- **旧数据兼容**：升级前遗留的旧单桶 `{success, fail}`（无维度键）读取时自动并入 search 维度（旧数据搜索占主导，权重 10% 影响小）。

### 5.7 播放失败换源增强：解析预验证（2026-10-23）

问题现象：部分歌单能正常显示（getMusicSheetInfo 多源兜底成功），但点歌播放失败。
