# 多音源管理用户走查报告

- 应用：极悦界（Jiyuejie，MusicFree fork），版本 0.6.2.15
- 走查视角：装了多个音源插件、频繁遇到源挂/需登录/限流的真实用户
- 走查方式：通读源码做"用户视角功能走查 + bug 审查"。本环境无 adb/模拟器/真机（updates/ 有 release APK 但无法安装运行），未实际点击界面；所有"观察"均来自源码静态阅读。
- 只读约束：未修改任何代码、未构建、未跑 npm/expo。

---

## 1. 画像与使用场景

- 我是重度多音源用户，手机里同时挂了洛雪系/网易系/QQ 系等若干 JS 插件。
- 高频痛点：某个源今天突然挂了/要登录/被风控限流；首页歌单来源今天打不开；想知道"哪个源还活着"；切换/停用某个源后搜索结果要立刻生效；一个源播不了要能自动换别的源。
- 本版与多音源相关的能力（从源码确认）：音源启停/拖拽排序/按可用率排序、多源并行搜索按源分 Tab、播放前匹配"我们的源"（playMatcher，≤2 源、缓存、熔断）、推荐歌单/排行榜走网易/QQ 公开接口 + 每日缓存、音源可用率统计。

## 3. 确定 bug 清单

> 严重度 | 文件:行号 | 触发条件 | 后果

### P1-1 插件歌单详情第 2 页起被 `isUseful` 误判，加载更多必进错误态
- 文件:行号：`src/pages/pluginSheetDetail/hooks/usePluginSheetMusicList.ts:22-32`
- 触发条件：进入一个插件推荐歌单详情，下滑加载第 2 页；来源插件正常返回一页歌曲且 `isEnd=false`（即还有第 3 页，属于合法中间页）。
- 代码：`isUseful` 对 `page>1` 只在 `result?.isEnd === true` 时返回 true：
  ```
  if (page === 1) return listLen > 0;
  return result?.isEnd === true;          // ← 拒绝了"非空但有下一页"的合法结果
  ```
- 后果：第 2 页有数据却被判"无用"，`resolveSheetDetail` 继续去试其他异平台插件（对该歌单必然返回空/报错），最终返回 null → catch → 请求态置 ERROR。用户在详情页下滑即看到"加载失败"，且无法继续翻页。正确判定应为 `listLen > 0 || result?.isEnd === true`。

### P1-2 音源管理卡片完全不显示"插件已损坏/版本不兼容"状态
- 文件:行号：`src/pages/setting/settingTypes/pluginSetting/components/pluginItem.tsx:130-214`
- 触发条件：懒加载插件延迟挂载失败（`core/pluginManager/index.ts:180-201` catch 后 `state=Error`），或插件 `checkValid` 版本不匹配（plugin.ts:1035-1048）。
- 代码：旧 Accordion（本文件 215-253 行注释保留）原本会渲染"插件和 app 版本不兼容 / 无法解析插件"；新卡片 UI 从头到尾没有读 `plugin.state` / `plugin.errorReason`，只显示名称、版本、可用率标签、开关。
- 后果：一个已经挂掉的源在管理页看起来"正常"（名称/版本来自 MMKV 缓存），多音源用户无法一眼识别哪个源坏了，只能靠搜索无结果反推，与"失效源要有明确提示"的核心诉求直接冲突。

### P2-1 搜索结果 Tab 的 `renderScene` 缓存依赖缺失，启停源后可能渲染错位
- 文件:行号：`src/pages/searchPage/components/resultPanel/resultSubPanel.tsx:76-79`（`useMemo(() => getSubRouterScene(...), [props.tab])`），配合 132 行 `export default memo(ResultSubPanel)`。
- 触发条件：在搜索页期间启用/停用了某个可搜索插件 → `routes`（70 行每次重算）变化，但 `renderScene` 因 deps 只有 `tab` 不重建，SceneMap 仍用旧 route key 集合。
- 后果：新启用的源 Tab 在旧 scene map 里找不到对应 scene，可能落到 DefaultResults 或空白。（代码层面 deps 确缺；是否必现需真机验证，暂列 P2。）

### P2-2 "全部更新音源"只更新已启用的源
- 文件:行号：`src/pages/setting/settingTypes/pluginSetting/views/pluginList.tsx:305`（`const plugins = PluginManager.getEnabledPlugins();`）
- 触发条件：某个源已损坏被我手动停用，但它出了新版本能修复；我点"更新全部"。
- 后果：被停用的坏源不在更新列表里，永远不会被批量更新，只能逐个进卡片手动更新（卡片更新按钮不过滤启用状态，pluginItem.tsx:84-91）。与"坏源最需要更新"的场景相悖。

### P2-3 多源并行搜索没有单源总超时，挂起的源 Tab 永久转圈
- 文件:行号：`src/pages/searchPage/hooks/useSearch.ts:109-113`（直接 `await plugin?.methods?.search?.(...)`，无 Promise.race）
- 触发条件：某插件内部不走默认 axios（默认 2s 超时，plugin.ts:36），而是用了一个不返回的自定义请求/回调。
- 后果：该源的搜索状态停在 `PENDING_FIRST_PAGE`，Tab 一直 loading，用户只能干等或切走。（默认 axios 2s 能兜住大多数 JS 插件，故列 P2。）

### P2-4 全局 axios 默认超时 2000ms，慢源被误记为"搜索失败"
- 文件:行号：`src/pages/../core/pluginManager/plugin.ts:36`（`axios.defaults.timeout = 2000`），插件经 `packages.axios`（plugin.ts:60）共享该实例。
- 触发条件：某个国内音乐源接口正常但响应 >2s。
- 后果：插件请求被 2s 掐断 → useSearch catch 里 `recordResult(platform, false)` → 该源可用率被拉低，进而被"按可用率排序"排到后面，形成"慢但可用"的源被系统误淘汰。属 MusicFree 上游默认值，对多音源用户有实际体感。

### P2-5 列表 keyExtractor 混入数组 index，分页后可能复用错位
- 文件:行号：`src/pages/searchPage/components/resultPanel/resultWrapper.tsx:36`（`` `${i}-${item.platform}-${item.id}` ``）；`src/pages/apiSheets/index.tsx:167` 同样模式。
- 后果：分页 concat 后 index 位移，长列表快速滚动时偶发 item 渲染错位/不刷新。

## 4. 可优化建议

### P1（功能性）
- **搜索缺"全部源合并去重"视图**：resultSubPanel 只按源分 Tab（resultSubPanel.tsx:70-91），没有一个"聚合 Tab"把所有源结果按歌曲合并去重。多音源用户最常想要的是"一次搜完直接看最佳命中"，现在要左右切 Tab 自己对比。
- **插件详情歌单无法手动刷新**：`core/api/cache.ts:105-127` 歌单/榜单详情按天缓存（`sameDay`），当天内没有单歌单刷新入口；遇到当天拉取到一半坏数据只能等明天。

### P2（体验/细节）
- **音源管理页无"一键健康总览"**：pluginItem 虽然显示可用率百分比（pluginItem.tsx:155-167），但该数字只在卡片挂载时读一次（48-66 行 effect，`[plugin]`），用久了不刷新；pluginSort.tsx 里反而有完整可用率视图。建议管理卡也随用随刷新。
- **推荐歌单二级页"手动指定源"不响应外部改源**：`recommendSheets/index.tsx:48` 在 render 时读一次 `Config.getConfig("plugin.recommendSource")`，之后外部（首页来源面板）改了来源本页不重排。
- **网易/QQ 接口歌单详情不分页**：`apiSheetDetail/index.tsx` 一次性 `getCachedSheetDetail`，网易 `/api/v3/playlist/detail` 只取 `playlist.tracks`（netease.ts:93）、QQ 榜单写死 `song_num=50`（qq.ts:106），大歌单/长榜单拿不全，且没有加载更多。
- **playMatcher 注释自相矛盾**：playMatcher.ts:43 写"失败缓存 15 分钟"，278 行 docstring 写"失败 24h"；代码实际是 15min（FAIL_TTL）。改注释即可。
- **热门搜索串行降级无总超时**：`searchPage/common/hotSearch.ts:116-128` 顺序尝试 QQ→网易web→网易旧版，每个 fetch 无 AbortController，某通道挂起会拖住整个热门词加载。
- **死代码**：`topList/components/topListBody.tsx`（per-plugin 榜单 Tab）已无任何路由引用（grep 仅自引用），现版排行榜走 apiSheets，可清理。

## 5. 未验证项（诚实声明）

- 未在真机/模拟器上跑过界面，所有"点击后看到/交互卡顿/转圈时长"均未实际验证；bug 描述为"代码静态阅读推断"，P1-1、P1-2 逻辑链路明确，P2-1 是否必现需真机确认。
- `getSortedPluginsWithAbility` 里 `getReliabilitySync` 在启动初期统计未加载完时返回默认 0.5（pluginReliability.ts:79-84），模块加载已 `void ensureLoaded()` 后台预载（pluginReliability.ts:252-253），但极端首帧是否仍平权未实测。
- 熔断窗口 `recordFailure` 的时间窗计算（playMatcher.ts:111-124）在跨多次失败 + 熔断恢复后的计数累加行为未做时序推演验证。
- 插件实际安装/更新/订阅拉取的网络行为（gitee 反爬、403）未实测；`updatePluginsFromSubscription` 的增量对比在版本号不可比时"保守下载"（index.ts:558-560）是否会重复下载未验证。
- 首页横滑推荐区、来源选择浮窗（home 相关组件）不在本次走查文件清单内，其与 `plugin.recommendSource`/`recommendSourceCache` 的联动未逐行核对。
