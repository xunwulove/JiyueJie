> 日期：2026-10-14 ~ 2026-10-15
> 来源：`E:\xunwu\Deepseek\jiyuejie\docs\均衡器接入与修复避坑记录.md`
> **演进**：本章记录的是**旧系统 AudioEffect（android.media.audiofx）均衡器**的接入避坑；2026-10-16 已切换为 **JamesDSP 音效引擎**（见 §2.7），旧链路不再作为主引擎，`SoundEffectModule` 仅保留注册做兼容兜底。

### 2.1 背景

按调研结论（MexMp3 开源播放器方案最贴近本项目）：**ExoPlayer + android.media.audiofx.Equalizer 绑定 audioSessionId**。
本项目播放器是 RNTP（react-native-track-player 4.1.1，ExoPlayer），RNTP 未开放 audioSessionId 与 audiofx 绑定，因此做了原生模块 `SoundEffectModule`，**用反射**从 RNTP 内部取 ExoPlayer 的 audioSessionId，再 `Equalizer(0, sessionId)` 绑定。

### 2.2 用户遇到的现象链条（按时间）

1. 均衡器入口找不到（0.6.2.11 装上后无入口）→ 已加设置二级页（音效设置）
2. 均衡器只有按钮、不显示频段/预设 → "点击播放音乐后"才出现频段调节
3. 预设音效不生效（只有"自设"一种）
4. 页面提示 `call attach first`
5. 播放后报 `诊断: Could not find @ReactModule annotation in com.doublesymmetry.trackplayer.module.MusicModule`
6. 播放后报 `诊断：InvocationTargetException → Player is accessed on the wrong thread. Current thread: 'mqt_native_modules', Expected thread: 'main'`

### 2.3 根因（4 个独立问题叠加）

#### 根因 1：ExoPlayer 主线程访问（最核心）
- ExoPlayer **非线程安全**，必须在创建它的**主线程**访问。
- RN 原生模块方法跑在 `mqt_native_modules` 线程，直接反射调 `getAudioSessionId()` 抛
  `Player is accessed on the wrong thread`，且被反射包成 `InvocationTargetException`（message 为 null → RN 侧只看到 "unknown."）。
- **修复**：`post` 到主线程执行 + `CountDownLatch` 同步等待（方法仍同步返回）；若已在主线程则直接执行（防自锁）。

#### 根因 2：RN 新版取 NativeModule 的方式
- `reactContext.getNativeModule(MusicModule::class.java)` 在 RN 新版要求模块类带 `@ReactModule` 注解；
  RNTP 老库没有 → 抛 `Could not find @ReactModule annotation`。
- **修复**：改按注册名取：`reactContext.getNativeModule("TrackPlayerModule") as? MusicModule`。

#### 根因 3：Android Equalizer 系统预设不可靠
- `SoundEffect.setPreset(index)` 依赖设备系统预设，**随 ROM 差异大、部分设备（车机/定制 ROM）为 0** → 预设音效"不生效"。
- **修复**：改为**内置 EQ 预设曲线**（`src/core/soundEffect.ts` 的 `EQ_PRESETS`，10 段、单位 millibel 约 ±12dB：摇滚/流行/爵士/古典/舞曲/重低音/电子/人声/高音增强 9 个 + 手动）。
  - UI 预设列表固定 = 手动 + 9 个内置，**跨设备统一**；
  - 应用预设 = 逐段 `setBandLevel(i, level)`（不再调 `setPreset`）；
  - 设备频段数少于 10 时取前 N 段近似（频段自低频到高频，截取方向一致）；
  - 切回手动按已存 `eqBands` 重放。

> 代码核对（2026-10-15，只读）：`EQ_PRESETS` 存在于 `src/core/soundEffect.ts:45`；逐段 `SoundEffect.setBandLevel(...)` 见于 `:137/:144/:171/:178/:189`；`getSoundEffectLastError()` 存在于 `:77`；持久化配置 `sound.eqBands` 见于 `:127/:176/:186/:188/:205/:207`。原生模块 `android/app/src/main/java/fun/upup/musicfree/soundEffect/SoundEffectModule.kt` 与 `SoundEffectPackage.kt` 均存在。

#### 根因 4：反射硬编码与设备兼容
- `queuedPlayer.javaClass.superclass.getDeclaredMethod("getExoPlayer")` —— kotlinaudio 是 JitPack aar 依赖，类层级随版本可能变化，superclass 硬编码会崩。
  **修复**：`findMethod()` 沿继承链向上查 `getExoPlayer` / `getAudioSessionId`（含私有方法）。
- Equalizer/BassBoost/Virtualizer 三个效果器**逐个独立 try**：个别 ROM（车机/华为）Equalizer 构造可能失败，不能一个失败连坐其余；失败原因记入 `lastError` 供诊断。

### 2.4 最终修复动作清单（本次生效的关键改动）

| # | 文件 | 改动 | 为什么 |
|---|---|---|---|
| 1 | `SoundEffectModule.kt` | `resolveAudioSessionId()`：主线程 post + CountDownLatch 同步等待 | ExoPlayer 必须主线程访问，RN 模块方法在 mqt_native_modules 线程 |
| 2 | `SoundEffectModule.kt` | `getNativeModule("TrackPlayerModule")` 按注册名取模块 | RN 新版要求 `@ReactModule` 注解，RNTP 没有 |

| 4 | `SoundEffectModule.kt` | `attach()`：三个效果器独立 try + `eqOk` 判定 + lastError | 设备兼容：一个失败不连坐；失败原因可诊断 |
| 5 | `SoundEffectModule.kt` | `buildFailureDetail(e)`：透传异常链（message/类名/cause 链，深度≤5） | InvocationTargetException 的 message 常为 null，必须带 cause 否则 RN 侧只见 "unknown." |
| 6 | `soundEffect.ts` | 新增 `EQ_PRESETS` 内置 9 预设曲线 | 系统预设随 ROM 不可靠/部分设备为 0 |
| 7 | `soundEffect.ts` | `applyAllConfig` / `applyEqPreset`：预设 = 逐段 `setBandLevel`（不再 `setPreset`）；切手动按 bands 重放；`setEqEnabled` 统一末尾 | 预设生效且跨设备统一 |
| 8 | `soundEffect.ts` | `lastError` + `getSoundEffectLastError()`；`getSoundEffectInfo` 不覆盖已有错误 | 页面可显示真实失败原因（区分"未 attach"与"attach 时设备报错"） |

### 2.5 避坑要点（以后接类似功能/改均衡器必读）

1. **RN 原生模块方法 ≠ 主线程**。任何访问 ExoPlayer/MediaPlayer/RNTP 内部对象的调用，先判 `Looper.myLooper() == Looper.getMainLooper()`，非主线程一律 post 回主线程 + 同步等待（CountDownLatch），否则必踩 "Player is accessed on the wrong thread"。
2. **RN 新版本取 NativeModule 用注册名**（`getNativeModule("TrackPlayerModule")`），不要用 `getNativeModule(Xxx::class.java)` —— 老库无 `@ReactModule` 注解会直接抛错。
3. **反射依赖第三方 aar 的类层级**：一律写"沿继承链查找方法"的通用函数，禁止 `superclass` 硬编码，依赖升级才不炸。
4. **反射异常必须透传 cause 链**：`InvocationTargetException` 的 message 常为 null，组装 `message/类名 → 最内层 cause` 再 reject，否则 RN 侧诊断全是 "unknown."。
5. **Android audiofx 预设不可依赖**：系统 Equalizer 预设（setPreset）随 ROM 差异大、部分设备为 0。要"预设"效果就自带曲线逐段 setBandLevel。
6. **audiofx 构造兼容**：Equalizer/BassBoost/Virtualizer 各自独立 try/catch，一个失败不能连坐；记录 lastError 供页面诊断，别只给 "call attach first" 这种误导文案。
7. **绑定时机**：audioSessionId 在播放器**首次播放后**才分配（RNTP 未播放过 → session 未创建）。`ensureSoundEffectAttached` 需在播放就绪后调用，页面加载时失败属正常，播放一次后自动绑定。
8. **设备频段数**：getBandLevelRange/getNumberOfBands 按设备返回，写 UI 频段条时以设备能力为准，内置预设按"截取前 N 段"近似。

1. **drflac 缓冲区溢出**：卷积器/FLAC 解码在极端输入下越界 → 加边界保护。

6. **use-after-free（CrossfeedProcess）**：交叉馈送对象生命周期与线程竞态 → 处理逻辑移入锁内。

8. **自绘滑块残影/黑屏**：圆球移动后旧像素残留（背景细轨道覆盖不了圆球区域）→ 曾用 `canvas.drawColor(0, CLEAR)` 清画布，但硬件加速下把整个 EQ 区域清成黑屏（只残留最后一条线）。**修复**：改用 `canvas.saveLayer(...)+restoreToCount` 独立绘制层，restore 时整层合成，旧内容不残留、也不黑屏。
9. **进阶音效滑块圆球绿色**：`@react-native-community/slider` 未设 `thumbTintColor` → Android 默认绿色圆球；需显式 `thumbTintColor={colors.primary}`。

## 第3章 启动页白屏问题与实现路径（反编译实测版）

> 状态：已修复（2026-10-12）；2026-10-13 复核修正（图标素材透明化 + 音符占比 + layer-list 去 gravity，见 §3.7）；此后经 v2/v4/v6 多轮迭代，最终态见 §3.11。
> 关联：极悦界（MusicFree RN 0.76.5 fork）Android 冷启动体验
> 本文档替代早期《极悦界-Android启动页技术调研报告》中"方案 C 推断部分"——该报告关于"大厂=系统 splash 纯色+圆形图标"的结论为**机制推断**，经反编译两大厂 APK 实锤后**修正**，详见 §3.3。
> 来源：`E:\xunwu\Deepseek\jiyuejie\docs\启动页白屏问题与实现路径.md`

### 3.1 问题背景

用户设备（华为平板 / 手机）冷启动「极悦界」时：
1. 点开约 **1 秒白屏**（系统 splash 阶段）；
2. 行楷"极悦界"文字**延迟出现/不出现**；
3. 桌面图标被裁切 / 嵌套显示；
4. 用户对照：QQ音乐 / 网易云"一点开就是品牌图+图标+文字"，无白屏。

### 3.2 根因（旧实现）

旧原生配置（`android/app/src/main/res/values/styles.xml`）：

```xml
<style name="Theme.App.SplashScreen" parent="Theme.SplashScreen">
    <item name="windowSplashScreenBackground">@drawable/splashscreen_background</item>  <!-- ❌ layer-list drawable -->
    <item name="windowSplashScreenAnimatedIcon">@drawable/splashscreen_icon</item>       <!-- ❌ 1536×1536 超规格 -->
    <item name="postSplashScreenTheme">@style/AppTheme</item>
    <item name="android:windowBackground">@drawable/splashscreen_background</item>
</style>
```

- `windowSplashScreenBackground` 传 **layer-list drawable**：违反 Android 12+ 官方契约（背景必须为**单一不透明色**）。华为等兼容层只处理纯色路径 → 白屏 / 近白屏；
- `splashscreen_icon.png` 为 **1536×1536**：官方 xxxhdpi 画布上限 1152×1152、可见圆 768px → 解码延迟 / 裁切异常；
- 行楷文字图放在 layer-list 背景层，白屏期间不可见。

### 3.3 反编译实测（决定性证据）

用户提供两个 APK，用 aapt2 反编译资源层（Manifest / themes / drawable / colors），结论如下：

#### 3.3.1 网易云音乐（6.2.81，com.netease.cloudmusic.iot）

|---|---|---|
| Launcher | 独立 `LoadingActivity`（非主界面） | Manifest MAIN/LAUNCHER |
| 启动画面载体 | 主题 `windowBackground` = layer-list | 主题 0x7f120011 → drawable/ii.xml |
| layer-list 内容 | 近白底 `#F9F9F9` + 红色氛围渐变（`#33FF3A3A→#00FF3A3A` 自下而上渐隐）+ 居中透明底品牌图（692×546 红白 logo） | drawable/ii.xml、color/tr、fp.xml、aet.png |
| 系统 splash 属性 | **零配置**（windowSplashScreenBackground / AnimatedIcon 全资源表 0x0101053x 零命中） | aapt2 dump resources |

#### 3.3.2 QQ音乐车机版（3.16.0.2，com.tencent.qqmusiccar）

#### 3.3.3 结论：大厂标准做法（与调研报告推断不符）

> **大厂根本不配置 Android 12+ 系统 splash 属性**（不走"纯色+圆形图标"路径）。

- **系统 splash**：保持默认（背景取 `windowBackground` 颜色 ≈ 白/近白，与品牌画面同色）→ 极短、几乎不可感知；
- **品牌画面**：全部由启动 Activity 主题的 **`windowBackground` = layer-list（纯色底 + 品牌整图 + 文字）** 承载——窗口一创建，windowBackground **先于一切布局立即全屏绘制**；
- 品牌图放 windowBackground 是**全屏窗口背景**，**非圆、不被圆形遮罩裁切**，这正是用户看到的"一点开就是品牌图+图标+文字"；
- 行楷/品牌文字在 windowBackground 的品牌整图内或启动 Activity 布局内。

#### 3.3.4 对旧实现的关键修正

- 我们之前把品牌整图放进了 **`windowSplashScreenBackground`**（系统 splash 属性）→ 违规 → 华为白屏；❌
- 正确位置是 **`windowBackground`**（Activity 窗口背景，合法、立即显示、非圆不裁切）；✅
- 系统 splash 只放**纯色**（合法契约），图标位**透明隐形**（避免圆形遮罩裁切 / 两段感）。

#### 3.4.2 启动时序（初版修复后）

```

  → 系统 splash（API31+）：纯色 #F1F4FA（合法、不白屏、无圆形图标）   [几十~几百 ms]
  → 窗口创建：windowBackground 立即全屏绘制 纯色 + 图标（fitCenter，非圆、完整）；行楷文字此时尚未出现
  → RN 首帧：BrandSplash 同色底 + 图标弹性适配 + 行楷文字淡入；bootstrap 完成后立即淡出（无 1500ms 强制停留）

```

#### 3.4.3 为什么这样是对的

- `windowSplashScreenBackground` 遵守官方"单一纯色"契约 → 华为/各 ROM 不再走异常路径 → **不白屏**；
- 品牌图标放 `windowBackground` → **立即显示、非圆、不被圆形遮罩裁切**（对齐网易云/QQ 实测）；行楷文字由 RN BrandSplash 在同色底上淡入，首帧即出现、无白屏等待；
- 系统 splash 图标隐形 → 无"圆形 logo → 整图"的两段突兀感；
- 两层（原生窗口背景 / RN BrandSplash）同色、同一图标（fitCenter ≈ contain）→ **切换无明显跳变**。

### 4.0 结论先行（5 条）

1. **Android 12+（API 31+）系统 splash 官方契约 = 纯色不透明背景 + 居中圆形蒙版图标 +（底部 200×80dp 品牌条，官方不推荐）**。"全屏品牌图 / 渐变背景"系统层做不到，只能靠 `windowBackground`（layer-list / 整图）或首帧自绘页。
2. **开源音乐 App 没有一个做"全屏整图启动页"**。主流"无白屏"做法 = `windowBackground` 用 layer-list（纯色底 + 居中 logo），或纯色；Signal / Nextcloud 用"系统 splash 背景与 windowBackground **同一 color 资源**"实现无缝衔接。
3. **`windowSplashScreenShortTimeout` 不存在**（官方文档可配属性清单里没有它，AAPT 会报 attribute not found）——纠偏，勿写入 styles.xml。
4. **`windowSplashScreenBrandingImage` 开源社区几乎无人使用**（调研 7 个 App 零使用；MusicFree 上游模板带它只是 expo 默认值），Google 官方设计指南明确不推荐。
5. **RN 生态**：expo-splash-screen 现代分支 = `androidx.core:core-splashscreen` 的封装（正确路线，本项目同路线）；crazycodeboy/react-native-splash-screen = Dialog 遮罩 hack，API 31+ 会"系统 splash + Dialog"双段闪烁，**勿用**。

| VLC | `@android:color/transparent`（透明 StartActivity 跳 Main） | 系统默认（launcher icon） | `application/vlc-android/res/values/styles.xml` |
| Auxio / Aegis | 不设置（Material3 默认） | 系统默认 | `values/styles_core.xml`、`values/themes.xml` |
| Signal | `@color/signal_colorBackground`（纯色） | `windowSplashScreenBackground=@color/signal_colorBackground`（**同一 color resource**）+ AnimatedIcon=vector | `values/themes.xml` + `values-v31/themes.xml` |
| Nextcloud | `@color/primary`（Launcher 主题） | `Theme.App.Starting`(parent=Theme.SplashScreen) + `windowSplashScreenBackground=@color/primary` + `postSplashScreenTheme=Theme.ownCloud.Launcher`（其 windowBackground 同 `@color/primary`） | `app/src/main/res/values/styles.xml` |

要点：
- **无缝衔接的核心 = 同一个 color resource**：系统 splash 的底色和窗口第一帧底色用同一资源（Signal、Nextcloud 都是）。我们 v6 已按此落地（`@color/brand_splash` 同时被系统 splash 背景和窗口背景渐变顶部引用）。
- **为什么品牌图放 windowBackground 而不是 windowSplashScreenBackground**：后者官方只收纯色；`windowSplashScreenAnimatedIcon` 又被 240/288dp 圆形蒙版裁切——"全屏品牌图"在系统层无处可放，只能走 windowBackground layer-list（或首帧自绘页）。
- **开源社区没有任何 App 把整张品牌设计图全屏铺进 windowBackground**：Retro Music 的 logo 也是"居中不拉伸"，四周露主题色。

> 注：上表"Retro Music / Metro 系统 splash（v31）= 无（targetSdk 29）"为网页级调研结论，附录 §4.6 真实克隆核验已推翻（Retro 实际 targetSdk 36、Metro 33，均有 values-v31），以 §4.6 为准。

#### Q2 `windowSplashScreenBrandingImage` 的真实用法与规格

- 调研 7 个 App（Retro/Metro/VLC/Auxio/Signal/Nextcloud/Aegis）**零使用**。
- 官方规格：**200×80dp**，屏幕底部居中；内容须透明背景；官方原文 *"the design guidelines recommend against using a branding image"*（设计指南不推荐）。
- 生态中唯一典型落地者 = flutter_native_splash（`android_12.branding` → `@drawable/android12branding`，README 要求源图 800×320px，即 xxxhdpi 下的 200×80dp）。
- MusicFree 上游模板带 400×160 branding 图 = **expo 模板默认值，不是开源社区主流做法**，可考虑删除。

#### Q3 `windowSplashScreenShortTimeout` 与 RN/Flutter 库源码机制

**`windowSplashScreenShortTimeout` 纠偏**：官方可配属性清单只有 6 项（Background / AnimatedIcon / AnimationDuration / IconBackgroundColor / BrandingImage / Behavior）+ 兼容库的 postSplashScreenTheme，**没有 ShortTimeout**。启动画面"自动结束"的真实语义 = ①应用画出首帧即关闭；②系统内部兜底超时（官方只说 "times out automatically"，未公开毫秒数、不可配置）。写入 styles.xml 会 AAPT 报错。

**expo-splash-screen（现代分支）** = AndroidX `core-splashscreen` 的封装：
- native 调 `installSplashScreen()`（SplashScreenManager.kt），MainActivity 注入 `SplashScreenManager.registerOnActivity(this)`
- config 插件生成 `Theme.App.SplashScreen`（parent=`Theme.SplashScreen`），写 `windowSplashScreenBackground` / `windowSplashScreenAnimatedIcon` / `postSplashScreenTheme=@style/AppTheme` / `windowSplashScreenBehavior=icon_preferred`；**不直接写 windowBackground**（AndroidX 父主题在 API<31 内部接管）、**不写 windowSplashScreenIconBackgroundColor**（要圆形底须业务自己补）
- 隐藏机制双保险：ReactMarker `CONTENT_APPEARED` 自动隐藏（仅当没 prevent 过）+ OnPreDraw 拦截 contentView 绘制兜底；退出 400ms alpha 淡出
- **没有超时兜底**：JS 调了 `preventAutoHideAsync()` 但 bundle 失败/崩溃时启动屏永久停留——业务须自补超时

**react-native-splash-screen（crazycodeboy）** = Dialog 遮罩 hack：`new Dialog(activity).setContentView(R.layout.launch_screen)` + `windowIsTranslucent=true` 透明窗口盖图，完全不碰 windowBackground；API 31+ 系统 splash 先弹 → Dialog 再盖 = 双段闪烁；无自动隐藏、无超时。**本项目不要混用。**

**flutter_native_splash（2.4.8）** = 不"画"启动图，只做：①PNG 按 5 个 dpi 桶切图落 `drawable-*`；②XML 模板拼 `launch_background.xml`（layer-list，底层 `<bitmap gravity="fill">` 支持整页背景图，中间 logo `gravity=center`，底部 branding 可加 padding）；③往 `LaunchTheme` 塞 `windowSplashScreen*` 属性（API31+ 走 `values-v31`）。**不生成 postSplashScreenTheme**（那是 core-splashscreen 兼容库的），由 Flutter 引擎首帧后自动切 NormalTheme。API31+ 整页背景图 `background_image` 不生效（README 明确）。

#### Q4 全屏 PNG 的屏幕适配（16:9 / 20:9 / 平板不拉伸）

- 开源社区的选择：**回避整图**——纯色底 + 居中 logo（`android:gravity="center"` 不拉伸）+ vector 渐变背景。
- 整图场景的正确姿势（综合官方机制）：
  - `drawable-nodpi/`：避免系统按密度缩放；
  - `.9.png`（9-patch）：把可拉伸区放在纯色/渐变区、关键内容区设不可拉伸——真正"整图适配所有比例"的解法；
  - `sw<N>dp` 限定符（如 `drawable-sw600dp/`）：为平板单独出图；
  - scaleType：用 `centerCrop`（fill 视图裁剪）或 `gravity="center"`（原尺寸居中），**不要 `gravity="fill"` 硬拉**。
- expo 出图规格：`canvasSize = 288 * multiplier`（Android 12 图标总窗口 288dp）× mdpi~xxxhdpi 五档，logo 默认 100dp 居中，深色模式 `drawable-night-*` 全档位。

### 4.4 结论清单：要补什么（✓ 已做 / △ 建议 / ✗ 不要做）

1. ✓ **windowBackground layer-list 全图（v6）**：PageBackground 同款渐变背景 + 渐变圆角容器 + 白音符 + 品牌名，品牌图与软件内一致。
2. ✓ **系统 splash 纯色与窗口背景同源**（`@color/brand_splash` 同一资源）——Signal / Nextcloud 的核心做法，三段零跳变。
3. ✓ **渐变只放 windowBackground**（系统 splash 层官方仅纯色，依据见分报告 03 §2.4）。
4. △ **expo-splash-screen 无超时兜底**（两个库都没做、必须自己补的坑）：建议在 `src/entry/bootstrap/bootstrap.ts` 的 `preventAutoHideAsync()` 后加 3~5s 超时 `hideAsync()`，防止 bundle 加载失败时启动屏永久停留。
5. △ **深色模式 night 变体**：windowBackground 现无 `values-night` / `drawable-night` 变体（系统 splash 深色下仍浅色 = 既有决策）；如要深色跟随，需补整套 night 资源。
6. △ **AnimatedIcon 可换 vector**（Signal 做法，免 PNG 被 mask 裁切的边缘风险，免多档切图）——可选优化。
7. △ **`android:statusBarColor="@android:color/transparent"`**（Retro Music 做法，启动期状态栏不突兀）——可选。
8. ✗ **不要用 `windowSplashScreenShortTimeout`**（官方不存在，AAPT 报错）；**BrandingImage 不启用**（官方不推荐、开源零使用）；上游模板的 branding 图可考虑删除。
9. ✓ **未混用 Dialog 遮罩方案**（crazycodeboy 坑）、**未加 `windowIsTranslucent`**（那是 Dialog 方案才需要的，加了对系统 splash 反而有害）。
10. ✓ **出图规格**：既有音符素材 1298×1298 透明底白音符（音符≈100% 画布，容器内 78%），符合 288dp 画布思路，未被 mask 裁切。

#### 4.6.4 用户核心问题归纳：开源 App"无缝自制图、看不出系统纯色"的四类机制

1. **第一帧就是自制画面（API<31 旧轨）**：`windowBackground`=layer-list（纯色满屏 + 居中 logo），窗口创建即品牌画面，系统根本没有"白底"帧可露——Retro/Metro 旧轨与国产软件反编译（网易云/QQ 车机）同款范式。
2. **同色系/同源色（API≥31 新轨）**：系统 Splash 背景不设（Retro/Auxio 赌 Material3 surface 系）或显式同源（Signal/Nextcloud 用同一 color resource），落地第一帧 `?colorSurface` → 两段同色系无跳变。
3. **品牌图标替换系统图标**：`windowSplashScreenAnimatedIcon` = 自制（动画）矢量/PNG，系统拿到的不是默认 launcher 图标——图标层也不露馅（Retro/Metro `avd_splash` 411dp、Auxio `ic_splash_anim` 432dp）。
4. **主题切换提前**：`onCreate` 在 `super.onCreate()` 前 `setTheme(真主题)`，启动主题停留压到最短。
5. 反面：Phonograph 什么都不做 → 白底/跳变可见。

#### 4.6.5 对极悦界（v6）的更新结论

- 当前 v6 = 机制 1+2+3 全占：`windowBackground` layer-list（渐变 + 渐变圆角容器 + 白音符 + 品牌名）、系统 splash 纯色 `#F8F9FA` 与渐变顶部**同一 color 资源**（`@color/brand_splash`，Signal/Nextcloud 级显式同源，4 个开源项目没有一个做到）、自绘白音符图标。横向对比属最完整组合。
- 4 个开源音乐 App 没有一家做"全屏整图启动"——它们靠"纯色/同色系 + 居中 logo + 品牌图标动画"营造无缝；极悦界 v6 的 layer-list 品牌画面已超过它们绝大多数，与国产软件反编译范式同一档。
- 可借鉴补强（建议项，未改代码）：① `windowSplashScreenAnimatedIcon` 未来可换 vector/animated-vector（Retro 411dp `avd_splash` 做法），免 PNG 密度档；② Retro/Metro 的"提前 setTheme"角色在极悦界由 expo-splash-screen 承担（JS 就绪后 hide，等价）；③ BrandingImage 确认 4 项目零使用，上游模板 400×160 可删；④ `windowSplashScreenShortTimeout` 确认不存在、零使用。

## 第6章 Gitee 发版上传避坑（0.6.2.13/0.6.2.14）

> 记录时间：2026-10-15。范围：Gitee Release（tag `latest`）作为软件更新仓的上传操作。
> 涉及文件：`src/utils/checkUpdate.ts`（更新链路固定依赖 `latest` tag 附件直链）。

### 6.1 坑一：旧附件删除 API 404（0.6.2.13 遇到）

**现象**：想先删旧附件再传新的，`DELETE /repos/{owner}/{repo}/releases/{id}/attach_files/{asset_id}` 返回 **404，不可用**。

**当时对策**：改走"同名覆盖上传"（直接传同名文件）。结果在 0.6.2.13 看似成功，实际埋下了坑二。

### 6.2 坑二：同名覆盖实为新增同名附件（0.6.2.14 遇到）

**现象**：0.6.2.14 上传新 `version.json`/APK 后，实测 `https://gitee.com/xunwulove/jiyuejie/releases/download/latest/version.json` 下载到的**仍是旧版内容**（0.6.2.13 的 changeLog）。

**根因**（API 实证，列出 release 附件列表后确认）：
1. Gitee `attach_files` 接口**不覆盖同名附件，而是新增一个同名附件**（同名文件并存，release 里出现两个 `version.json`）；
2. 下载直链解析到**第一个（旧的）**附件 → 软件内"检查更新"永远命中旧版本。

**附加坑（同轮）**：`attach_files` 的 `name` 参数**被忽略**，附件名 = 本地文件名。若本地文件叫 `version-0.6.2.14.json`，上传后附件名就是 `version-0.6.2.14.json`，更新直链 404。**对策：上传前先把本地文件复制/命名为目标文件名**（`version.json` / `app-arm64-v8a-release.apk` / `app-universal-release.apk`），不依赖 name 参数。

### 6.3 标准发版流程（已验证）

每次发版（更新 version.json + APK）采用**重建 release**，不要"同名覆盖"：

```
1. DELETE /repos/xunwulove/jiyuejie/releases/{id}?access_token=...   # 删整个 release（tag latest 保留），204 成功
2. POST   /repos/xunwulove/jiyuejie/releases                          # 重建：tag_name=latest、target_commitish=master（必填，缺了 400）、name、body、prerelease=false → 201，记新 id
3. POST   /repos/xunwulove/jiyuejie/releases/{新id}/attach_files       # 分三次传：version.json / app-arm64-v8a-release.apk / app-universal-release.apk（本地文件必须已命名成目标名）
4. 验证：curl -L 三个直链均 200，version.json 内容 = 新版本号（防 CDN 缓存读旧）
```

同步事项：
- 仓库文件 `updates/version.json` 也要更新（兜底地址）：`PUT /repos/xunwulove/jiyuejie/contents/updates/version.json`（需先 GET 拿 sha）。
- token：用户账号 xunwulove，gitee token 存于本会话记忆（勿写入公开文档）。
- 环境注意：本机 PowerShell 下 `curl -w` 等命令输出**时有时无**，判断结果以落盘文件 + Read 为准。

### 6.4 坑三：创建 release 的 `body` 必填 + 遗留 tag 冲突（0.6.2.15 实测）

**现象 A**：重建 release 时，无论 JSON / urlencoded / multipart 哪种 body 格式，`POST /releases` 一律返回 `400 {"messages":["body is missing"]}`。

**根因 A（body 字段必填）**：Gitee 创建 release 的 `body`（release 描述）字段为**必填**；缺失时统一报 "body is missing"（看似请求体缺失，实为字段缺失）。**对策：请求必须带 `body`**，传版本号（如 `极悦界 0.6.2.15`）即可，无需长文。

**现象 B**：`DELETE /releases/{id}` 只删 release，**不删 tag**；`latest` tag 仍留在 refs（`git ls-remote origin "refs/tags/*"` 可见）。此时重建同名（tag_name=latest）release 同样失败。

**根因 B（遗留 tag 冲突）**：tag 已存在时创建同名 release 会冲突。**对策：重建前先删遗留 tag**：

```
git push origin :refs/tags/latest        # 删远端 tag；确认 git ls-remote 中 latest 已消失
```

删净后再 POST 创建 release（`body` 必带）→ 201，记新 id，再传三个附件并 curl -L 验证。

### 6.5 经验：同版本号重发双 release 重建（0.6.2.15 重发，2026-10-17）

**背景**：不升版本号重发时，`latest` 与唯一版本 tag（`v0.6.2.15`）两个 release 都要重建——checkUpdate 主地址读 `latest/version.json`，APK 直链则指向唯一版本 tag（见 `src/utils/checkUpdate.ts` 注释）。

**操作序列（一次成功）**：
1. `DELETE /releases/{latest_id}` 与 `DELETE /releases/{v_id}`（204 ×2）——只删 release 不删 tag；
2. `git push gitee :refs/tags/latest :refs/tags/v0.6.2.15`（一条命令删两个 tag；`git ls-remote gitee "refs/tags/*"` 确认只剩历史 tag）；
3. 写 UTF-8 的 release 创建 JSON（`tag_name`/`target_commitish=master`/`name`/`body`/`prerelease`），`curl --data-binary @file -H "Content-Type: application/json"` POST（201 ×2，记新 id）；
4. 每个 release `POST .../attach_files -F "file=@本地路径"` 三次（version.json / app-arm64-v8a-release.apk / app-universal-release.apk，201 ×6）；
5. `PUT /contents/updates/version.json` 与 `PUT /contents/README.md`（先 GET 拿 sha，content=base64，UTF-8 无 BOM）200；
6. 验证：`curl -L latest/version.json` 内容为新 changeLog；`curl -I -L` 两个 APK 直链 200；`raw/master/updates/version.json` 200。

**坑**：release `name` 中文曾显示乱码（0.6.2.15 首版），根因是 JSON body 经 PowerShell 直接传参的编码问题——**必须写 UTF-8 文件 + `--data-binary @file` 发送**，本次 name/body 中文正常。
